I've read both scripts, both schemas, their binding helpers (`link_observations.py`, `reviewed_voice.py`), the content-brief contract, the tests, and the fixtures. Here is an adversarial review focused on **evidence binding and invalidation**.

## Summary of the binding model

Both modules follow the same pattern: a JSON artifact binds sub-objects by `{path, sha256}`; `bound_bytes()` verifies the digest and path safety (`resolve_bytes`, no `..`/absolute/symlink/escape); validation then re-derives claims from the bound bytes. That core is **solid** — digest invalidation is real, and the tests prove it (`test_outcome_tracks_exact_answer`, `test_publisher_validates_staged_evidence_and_resume`).

The weaknesses are almost all at the **edges of the chain**: what is *not* bound, what the binding *proves*, and self-referential anchors.

## Findings

### H1 — `private` is enforced only at render time; the artifact stores the raw text (customer_questions.py:31-32, 97-101)
`sanitized_extract: true` is required for private rows, but the actual binding requires `row['passage'] in record['text']` (L40) — i.e. the stored `passage` must be the **verbatim, unsanitized** source substring. `render()` is the *only* place private fields are withheld. The machine artifact (`customer-questions.json`) still contains `passage` and `current_answer` in plaintext, and `--out` writes a redacted view while the JSON is published as-is.

- Semantic contradiction: the flag claims "sanitized extract," the validator demands the passage be the *un*sanitized text.
- A private question therefore leaks if the JSON (not the rendered markdown) is shared. `validate`/`render` never guarantees the withheld content is absent from the artifact.

### H2 — The analytic field that drives the headline result is **not** evidence-bound (creative_evidence.py:17, 77, 82-85)
`OBSERVED` binds `url, creator, platform, format, language, market, published_at, observed_at, distribution, metrics`. `hook` and `pattern` are deliberately excluded. But `pattern` is exactly what `compare()` uses to build the `patterns`/`replicated` output (L82-85) — the module's central comparative claim ("replicated: len(distinct creators) >= 2"). So the one interpretation that produces the quantified signal can be set arbitrarily with no source support. This is thematically consistent with "hypotheses only," but the binding does not enforce that boundary; nothing distinguishes a source-supported pattern from an invented one.

### H3 — `tests` are free-form: `held_constant` is never enforced (creative_evidence.py:50-54, schema:287-294)
`validate` only checks that `example_ids`/`counterexample_ids` exist in `by_id`. It does not check that a test's examples:
- share a cohort (same platform/format/language/market/distribution),
- actually hold the claimed `held_constant` fields constant,
- avoid esoteric `excluded` (unknown-distribution) examples.

So a "controlled" test can compare examples across different platforms/markets and still pass, and `compare()` copies `tests` verbatim into the output (L90-91) with no flag. The schema's `held_constant` is an unverifiable string list.

### H4 — `validate_brief` never binds the brief's audience to the question's segment (customer_questions.py:80-86)
It checks `row['kind'] == 'customer'`, `segment_relation == 'target'`, and `brief_id in linked_brief_ids`. It never checks `question.segment == brief['audience_segment']`. A brief targeting "enterprise CTOs" can cite a reviewed target-customer question whose segment is "hobbyist students" — `segment_relation: target` is relative to the *question's own* segment, so this passes. That is an applicability-binding gap exactly where marketing claims are sourced.

### H5 — `linked_brief_ids` is a one-way, unvalidated back-reference (customer_questions.py:85)
The brief→question link is checked, but a question's declared `linked_brief_ids` are never validated against any brief. Forward references to nonexistent briefs pass. (Minor, but it means the "linked" relation is not a real cross-check in one direction.)

### H6 — Self-referential anchors: the chain proves internal consistency, not provenance
- `creative_evidence`'s `sources/*.json` is itself a hand-authored extract, not a capture record. `observed fields differ from retained source extract` (L39-40) only proves the author kept two files consistent — unlike `link_observations`, which binds to an HTTP capture with `parser_version`/`http_status`/`redirects`. There is no `capture_method`, `checked_at`, or tooling provenance on creative examples, so a fabricated metrics file passes cleanly.
- `customer_questions`' `review.json` is author-controlled and `review_voice()` validates **structure only** (its own docstring: "validates review structure, not the reviewer's interpretation"). Combined with the fact that `review` is just a digest-bound local file, a synthetically-authored review passes `test_fabricated_quote_and_supplier_cannot_be_customer`-style checks. The tests acknowledge this (fixtures are "Synthetic"), but the validator's error messages ("requires an accepted matching source review") overstate what is proven.

### M1 — Metric availability: `suppressed`/`unavailable` rows still enter cohorts (creative_evidence.py:41-47, 70-77)
`available` counts must be nonnegative ints; else must be `null`. But a row with `views.availability == 'suppressed'` (or `unknown`) is not excluded from a cohort — it just gets `null` ratios. A cohort can be "comparable" while every member's headline metric is unavailable. Only `distribution == 'unknown'` causes exclusion (L67-69). This under-captures the "no platform support" case.

### M2 — Cohort key over-constrains via the *entire* metric-definition set (creative_evidence.py:65-66)
`metric_defs` includes every metric name+definition. Adding a `comments` metric to one example that others lack splits the cohort (verified by `test_distinct_windows_definitions_and_unknown_creators` using a differing *definition*). The ratio only divides `saves/shares/comments` by `views`, so grouping should arguably key on the `views` definition (and each numerator's definition independently) rather than the union set. As written, a single extra annotated metric silently fragments otherwise-comparable cohorts — an under-grouping bias that suppresses replication.

### M3 — Replication counts distinct creators but ratios double-weight one creator (creative_evidence.py:79-88)
`patterns[p].add(creator)` requires ≥2 **distinct** creators for `replicated`, which is correct. But the `examples` list retains every row, so a single prolific creator contributes multiple high ratios to `examples` while the pattern still counts as one creator. Descriptive only, but the example set is not deduped or flagged, inviting over-reading.

### L1 — Outcome binding only ties to the answer text, not to provenance (customer_questions.py:53-61)
`outcome` must match `question_id` and `sha256(current_answer)`, an enum, non-empty `limits`, and tz-aware `observed_at`. But nothing ties the observation to the question's source/segment/context. An actor can set `current_answer` and a consistent `outcome` with zero relationship to the sourced evidence — the "observed result" is bound only to a free string. Acceptable given it's an internal artifact, but it is not evidence-bound.

### L2 — `outcome` / `review` sub-documents have no schema; validation is ad-hoc (customer_questions.py:54-61)
The row schema types `outcome`/`review` as `{path, sha256}` only. The *content* is checked field-by-field with `KeyError`/`AttributeError` caught into a generic message (e.g. `'observed_at'`). Missing-field errors surface as opaque strings rather than named violations, and any extra fields in the outcome JSON are unconstrained.

### L3 — Markdown render escaping is incomplete (customer_questions.py:94)
`cell()` escapes `|` and newlines only. A value containing a backslash before a pipe (`\|`) becomes `\\|`, re-opening a table column; `<`/backtick/heading injection likewise pass through. Low severity (internal report), but the escaping is not robust.

### L4 — Minor inconsistencies
- `validate_brief` builds its contract validator **without** `FormatChecker` (customer_questions.py:71) while the main validators use it. No formats are declared in that sub-contract today, so it's latent only.
- `creative_evidence.validate` does not check `tests[].id` uniqueness (schema doesn't require it either).
- `source_date` (null allowed, "null means unknown") is compared with `!=` to `record['published_at']` (L42). A source with a known `published_at` therefore *cannot* carry an "unknown" `source_date`; the "null means unknown" message is only reachable when both are null. Possibly intended strictness, but the error text oversells the semantics.

## What's genuinely good
- Path safety in `resolve_bytes` (rejects `..`, absolute, backslash, symlinks at every hop, and post-resolve containment) is careful and shared by both modules.
- Digest invalidation is enforced on edit for source/review/outcome/artifact, and the publish/resume tests exercise staged-vs-persisted equivalence.
- Type-strict count checks (`type(value) is not int` correctly rejects `bool`, `nan`, `inf`, `1.5`) and the "unavailable ⇒ null" rule are correct.
- Zero-view division is guarded, and `math.isfinite` prevents non-finite ratios reaching `allow_nan=False` serialization.

## Highest-impact fixes
1. **H1** — either make `visibility: private` redact at the artifact level, or rename the flag to reflect that only the *rendered* view is redacted and drop the "sanitized" implication.
2. **H2/H3** — add `pattern` (and the fields a test's `held_constant` names) to the bound set, and validate that a test's examples share a cohort; otherwise state explicitly in output that pattern/tests are unbound annotations.
3. **H4** — bind `brief.audience_segment` to `question.segment`.
