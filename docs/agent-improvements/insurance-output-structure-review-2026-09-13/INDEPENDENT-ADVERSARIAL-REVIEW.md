## Ranked findings

### 1. Selection and evidence revisions need distinct meanings and invalidation rules — must resolve

**Plan:** lines 27, 49–57, 87, 97–105. A nullable selection, selected scope/revision and review-required handoffs are promised, but the plan does not identify which changes advance which revision, or whether a corrected interpretation invalidates a previously passed research checkpoint. Changing research on B must not invalidate execution of A merely because the project manifest revision increased. Conversely, changing A's customer/problem/model must not retain its validation simply because its stable ID remains the same.

**Verified:** `scripts/route_workflow.py:47–74,77–102` accepts passed checkpoint metadata and, for strategy prerequisites, existing nonempty artifacts. It does not check a reviewed source or concept revision. `scripts/evidence_scout/workspace.py:299–322` replaces one checkpoint without invalidating dependent checkpoints. `scripts/brand/validate_business_to_brand_handoff.py:43–64` checks hashes of business context and optionally the strategy file, not corrections to the interpretation of a referenced source. A hash cannot detect an acknowledged interpretation error when original evidence bytes are preserved.

**Minimal remedy:** define selection generation separately from generic manifest revision; bind selected outputs to the case's reviewed concept/evidence revision. Put applicability/correction references in existing case assessment/checkpoint records. Specify that changed critical interpretations or scope mark affected passes and dependent plans/handoffs review-required, and block normal execution until reviewed. Existing overrides may waive named evidence prerequisites; they must not silently select a case, admit two selections, or accept an obsolete selection generation. No general dependency-graph service is needed: declared bindings and conservative invalidation within affected cases suffice.

**Acceptance:** A selected, B updated: A stays current. A corrected without changing source bytes: affected checkpoint and handoff fail freshness checks. Switch A→B→A: an old A handoff remains obsolete. An explicit pain override with no selection still cannot authorize execution. Unaffected cases and original evidence bytes remain unchanged.

### 2. Exploratory appraisal needs an explicit specialist contract — must resolve

**Plan:** lines 51, 65–73. Pre-pain feasibility/economics is necessary, but “using existing specialists” is not yet an executable route design. The same specialists currently produce plans with later-stage prerequisites.

**Verified:** `config/skill-catalog.json:398–418,442–463,515–534` binds startup, GTM and pilot strategy work to passed stages including problem validation. `scripts/route_workflow.py:244–282` applies those prerequisites by skill and scope; switching to focused scope suppresses strategy-stage checks but does not remove a route's pain gate. `scripts/enforce_skill_route.py:38–70` accepts only the existing scopes and recomputes the route. `scripts/evidence_scout/workspace.py:281–288` independently gates commitment-stage updates.

**Minimal remedy:** specify the appraisal route's owner, permitted supporting sections, stage requirements and output paths in the existing route/catalog contract. Make appraisal an explicit supported mode of the owning specialist, with no commitment-stage advancement and no root execution artifacts. Preserve the current full-strategy prerequisites. Do not rely on relabeling work focused or on prose that contradicts the specialist workflow.

**Acceptance:** an unvalidated, unselected case can receive hypothetical feasibility and economics; equivalent GTM/pilot execution remains blocked. Direct skill dispatch and CLI routing agree. Appraisal does not create full canvases, campaigns or an approved pilot as a side effect.

### 3. Project serialization is justified, but the existing helpers do not yet supply it — must resolve

**Plan:** lines 53–57. “Use existing locking/atomic-write patterns” understates the change needed for snapshots, current artifacts, decisions and manifests to publish coherently.

**Verified:** `scripts/project_workspace.py:53–77` checks a revision before an atomic file replacement, without a lock covering read/check/write. Two writers can both observe the same revision. `scripts/evidence_scout/workspace.py:96–113` has a research-manifest lock and a fixed temporary filename; it is not a project transaction. `resolve_run_dir` at lines 506–526 names runs to second precision, so concurrent identical topic runs can collide even if raw collection is declared parallel.

**Minimal remedy:** state which existing helper acquires the one project lock, require current-state publication callers to use it, and define the minimal pending-operation record, completed marker and idempotent resume behavior. Read and revision-check under the lock. Dispatch/consumers must refuse pending selected state; a timeline-only restriction is insufficient. Give concurrent raw runs exclusive run directories. These requirements do not need distributed transactions.

**Acceptance:** two conflicting selections yield one commit and one conflict; simultaneous same-topic collections cannot share a directory; interrupt after snapshot, after current-file replacement and before final manifest publication. Resume either finishes once or restores a clearly identified prior state, never publishes a mixed plan or duplicate decision. Test lock ordering if stage helpers are called inside publication.

### 4. Shared-source paths and legacy operation need a declared boundary — resolve before default rollout

**Plan:** lines 49, 55–57, 105. Explicit roots and a producer inventory are strengths. However, allowing shared sources outside a case while rejecting case path escapes requires separating input provenance from output allocation. “Legacy projects remain readable” also leaves unclear whether ordinary legacy continuation still writes through old paths or fails with a migration instruction.

**Verified:** `scripts/route_workflow.py:66–69` resolves checkpoint artifacts under the manifest's grandparent and requires containment there. With a nested case, a legitimate root shared study falls outside that case. `scripts/evidence_scout/workspace.py:261–265` alternatively permits absolute artifact paths; `resolve_run_dir:518–519` returns an explicit output directory without a workspace. The hook's business-workspace detection at `scripts/enforce_skill_route.py:51–58` looks for the root research manifest, which need not exist for a new case-only topic. Discovery at `workspace.py:421–442` likewise searches root research manifests.

**Minimal remedy:** define case-local assessment artifacts as checkpoint evidence, with explicit bindings to shared/legacy inputs; do not broaden write containment to accommodate reading shared sources. Define case plus `--out-dir` behavior and update discovery/hook detection in the producer checklist. State whether legacy writes remain supported under the old contract or explicitly require migration; never silently reinterpret an umbrella pass as a case pass.

**Acceptance:** nested case resume works without a root research manifest; shared input reads work while cross-case output writes fail; symlink escapes, unknown cases and case/output conflicts fail before writing. Include both legacy read and attempted legacy continuation in rehearsal.

### 5. Research-quality acceptance currently names a harness that cannot produce outputs — must correct the acceptance procedure

**Plan:** lines 77, 114. Fixed adverse evidence and manual inspection are appropriate. However, “run the existing eval harness on these tasks” can be mistaken for the listed `scripts/run_evals.py` command.

**Verified:** `scripts/run_evals.py:1–13,40–86` expressly validates dataset structure, not model execution or responses. There is also a demonstrated semantic failure worth testing: `projects/german-insurance-opportunity/README.md:11` says no cohort has won an adequately audited comparison, while lines 19–37 retain stronger motor rejection and an English-first ordered recommendation. This review identifies inconsistent current presentation, not which market judgment is correct.

**Minimal remedy:** name a small manual execution procedure using fixed local evidence, preserve actual responses and judge them against explicit assertions. Keep the structural command as a separate check. Add a follow-up correction task: the response and affected current sections must agree, with the superseded recommendation moved into history rather than left as current advice.

**Acceptance:** test the plan's complaint, job-posting, launch-spike and missing-cost fixtures; also test contradictory old/current recommendations, nontransferable country/segment evidence, and a correction that should not change the ranking. No claim of semantic success without inspecting generated responses. A new evaluation platform is unnecessary.

### 6. Economics is sensible, but define the smallest supported calculations before building the helper — worthwhile improvement

**Plan:** lines 83–91. The synthetic contribution and volume calculation is correct: (1,500 + 2,500) / (100 − 25 − 10 − 15) = 80; capacity 60 misses that target. Null unknowns, period alignment and separate founder opportunity cost are material strengths.

**Verified:** `scripts/strategy_review.py:47–70` calculates KPI ratios, not this economics model. A compact helper therefore has demonstrated novelty. Existing economic guidance in `references/strategic-positioning.md:20–32` already covers ramp, retained cohorts, acquisition/service labor and gross/net treatment; reuse it.

**Minimal remedy:** enumerate a transactional contribution/volume calculation and a bounded recurring cash/cohort calculation. Define revenue as the venture's receipt rather than pass-through customer spend, round required indivisible sales upward, identify costs already included in acquisition contribution, and require opening cash plus a time horizon before claiming runway sufficiency. Unsupported retention/payback cases should return unresolved, not trigger a larger finance framework.

**Acceptance:** include commission/pass-through distinction, noninteger required sales, cancellation/refund exposure where relevant, missing opening cash, immature cohorts and a delay that creates a cash deficit despite positive contribution. These are synthetic arithmetic tests, not insurance or financial advice.

## Review limits and disposition

No test suite, model evaluation, migration, paid provider, installation or execution smoke test was run. All concurrency and failure scenarios above are inferred from inspected code, not reproduced. No exhaustive producer or remote-repository audit, legal verification, license audit or economic input validation was completed. Revise the identified contracts and acceptance procedure; then implement the existing four packages with their stated synthetic-first rollout and explicit live-migration boundary. No additional work package is warranted by this review.
