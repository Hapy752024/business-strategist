# Expanded optional measurement plan

Status: finalized after fresh plan PASS and final implementation PASS; no live integration is being built or enabled. The user asked for web/GitHub best practices, optional analytics, optional A/B feedback to PostHog, Google/Meta campaign measurement and server-side robustness. All extend the original agent-setup task. Website foundation was separately plan-reviewed and tested; this expanded scope needs its own clean plan review before finalizing skill guidance.

## Decisions and changes

1. Keep one existing website builder with conditional references and checked routing. Do not install new orchestration/marketing frameworks. Keep analytics disabled when declined; unresolved preference pending; A/B measurement and ad tracking independently selected. Reuse existing Vercel fixture/flag path unless PostHog assignment is selected.
2. Research verified official documentation and implementation repositories. Record primary sources, checked date, reference path and scope, what was inspected versus executed, and gaps. Reference PostHog stable JS/Node APIs, GA4 Measurement Protocol and consent docs, Meta maintained SDK/API docs and transactional-outbox guidance. Do not copy unreviewed code or promise unsupported native GA4 connectors.
3. Finalize posthog.md, experimentation.md and campaign-tracking.md; add a focused implementation-reference table rather than vendoring SDKs. Capture selected account/project IDs, permissions, event names, consent, region, source-of-truth outcome, exposure-to-conversion identity, destination ownership, delivery/test proof and rollback. No secrets in chat/Git/client environment.
4. Hybrid measurement: browser for consented actual page/variant exposures; server for authoritative conversions. Use existing backend/queue and transactional outbox or justified reliable handoff when outcomes require robust delivery. Check consent at enqueue and dispatch, cancel after withdrawal, no replay of pre-consent activity, no invented attribution. Idempotent event IDs and platform-specific deduplication, bounded retries/backoff, event-age limits, rejected/unknown/pending receipts and dead letters. Protect ingress/webhooks and allowlist destinations. Do not create new backend infrastructure for a static site's basic analytics.
5. Separate product analytics from advertising purposes and export from spend import. GA4/GTM, Google Ads and Meta Pixel/CAPI have different identifiers/roles. Basic Google consent mode/no optional traffic is default; server-side and hashed data do not exempt consent. PostHog destination filters must enforce the advertising purpose. A/B protocol has predeclared fixed-horizon or valid sequential stopping, a single assignment authority, real exposure logging, stable identities, deduplication, consent-coverage bias and control-only fallback.
6. Provide practical project implementation sequence and test matrix based on official reference implementations. Use stubbed providers and consent/network/state tests first; live account connection/activation/test events only with explicit existing authorization. No unconditional installation, account creation, ad spend, GTM publish or winner rollout. Clearly distinguish proposed skill process from live acceptance.
