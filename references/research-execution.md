# Executing and closing customer research

Use this for a substantive customer/problem study or case rerun. A focused factual answer keeps the narrower task scope in `references/task-scope.md`. The checkers named below enforce the field-level contracts; their `--help` output is the procedure.

1. Resolve the selected project, case and run. Read the manifest, current `case_insights.md` and persisted founder questions. Record the requested decision and scope. Do not shrink a substantive assignment to a focused lookup because a convenient source was found. For a multi-case rerun, run this loop for **every** requested case. Register a multi-run assignment with `python3 scripts/case_workspace.py register-research` before treating any run as final, then `validate_research_completion.py --check assignment`. A historical source counts once at case level; adjacent/context studies cannot close target cells. A small source pack never closes a broader request.
2. Before calling providers, write or reuse the executable query plan and customer-feedback source matrix. Show the user the proposed jobs, roles, locales, source families, contrary/positive searches and the first bounded allocation. Query counts are initial work allocations, not quality or spend thresholds.
3. Verify relevant endpoints, using an actual content capture when available; a credential, balance or search-only check does not prove comment access. For project Firecrawl CLI calls use `python3 scripts/firecrawl_project.py ...`. Public Facebook capture requires the current signed review bundle. Preserve unavailable sources as gaps and try an applicable supported fallback.
4. Execute the planned queries and conversation capture. Inspect the query ledger, raw pages, comments and replies. For Reddit, check that selected discussions span the planned query intents; increase `--reddit-comment-posts` or refine when a material intent lacks customer conversations. Resume interrupted work with the same plan; a changed plan starts a linked follow-up.
5. Check collection: `python3 scripts/evidence_scout/validate_research_completion.py --workspace <root> --run-dir <run> --check collection --json`. Exit 0 proves the declared capture ran; it does not validate a customer claim. Follow `next_actions`. Search failures and valid empty results are different outcomes.
6. Review source-linked experiences, including a purposeful sample of rejected/adjacent material. Preserve original language, speaker, chronology, success and contrary cases. Build the experience ledger, source review, coverage, U/R synthesis and claim review (`references/customer-voice.md`). Separate creator/supplier voice from firsthand customer experience. Claims use only reviewed accepted items; sampled-out material cannot support prevalence.
   For a registered case, each low-yield or adjacent-only cell needs a `search_resolution`. After one bounded, targeted refinement that found neither a target episode nor a new public source route, mark it `primary_research_needed` instead of repeating broad search; a provider failure alone is access-limited, not exhaustion. Prepare a case-specific unpaid `market_research/interviews/recruitment-plan.md` from `templates/project/primary-research-handoff.md` and bind it in the source plan. The route is not completed interviews or outreach authorization. Every attempted query in a v4 target study needs its own query review; never mark a query `reviewed` because a different query looked useful. Optional prioritization view: `build_research_yield.py` (a derived view, not a completion receipt).
7. Bind refined or entity-specific capture runs in the source plan's `capture_inputs` only when they pass the collection check and match case, entity, locale and reviewed locator. Then run `validate_research_completion.py ... --check research --json` on the parent run. A reviewed `insufficient_evidence` outcome is valid research if execution was complete; it cannot pass `problem_validation`. A partial finding can be shared with named unfinished sources and limits, without a full-completion claim. The same original URL in adjacent and target ledgers counts once; an overlapping distinct interpretation is a conflict, not independent corroboration.
   After each review batch run `python3 scripts/evidence_scout/build_case_closeout.py --workspace <business-root> --case <id> --json`, work through its pending items, rerun the checks and publish reviewed insights progressively.
8. Update the case's one `case_insights.md` after each coherent batch (contract: [case-insights.md](case-insights.md)). A progress snapshot is useful but is not final delivery. Newly captured evidence must not enter claims before review. Short answers enter insights directly; substantial answers go under `market_research/deep_dives/` with their business implications in insights.
9. In the final handoff state executed scope, what reviewed episodes support, contrary cases, coverage gaps, claim readiness and the current insights path. If any check is partial or invalid, name the missing work and do not call the assignment fully rerun. Keep case-specific business-plan commitments behind the current problem-validation receipt.
   Keep each case queued until it has one explicit reviewed outcome: **provisional plan published**, **more targeted research required** (named open cell and distinguishing observation) or **evidence insufficient** (executed desk scope, exact missing observation, bounded primary-research handoff). An outcome is a progress label, not closure; do not label a case evidence-insufficient just because collection is complete. The strict stop check is `build_case_closeout.py ... --require-terminal`. Before final delivery run `--check assignment` and `--check delivery` and have a separate reviewer inspect original passages, roles, countries, numbers, counterevidence and omissions. A completed desk scope with `primary_research_needed` is an insufficient-evidence outcome, not a passed problem gate.

The completion checker is read-only and verifies provenance and coverage declarations; an analyst still judges what passages mean. Never infer market prevalence, demand or willingness to pay from comment counts, duplicate posts or a successful API call.
