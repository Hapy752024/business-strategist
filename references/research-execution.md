# Executing and closing customer research

Use this for a substantive customer/problem study or case rerun. A focused factual answer retains the narrower task scope in `references/task-scope.md`.

1. Resolve the selected project, case and run. Read the manifest, current `case_insights.md` and persisted founder questions. Record the requested decision and scope. Do not shrink a substantive assignment to a focused lookup because a convenient source was found.
   For a multi-case rerun, execute this loop for **every** requested case. Before and after each review batch run `python3 scripts/evidence_scout/build_case_closeout.py --workspace <business-root> --case <id> --json`. Its bootstrap queue reports an unregistered assignment and available completed captures; register the requested scope before interpreting the case as reviewed. A collection pass or current progress insight never counts as a terminal case outcome.
   For a registered case with multiple capture runs, register the whole assignment in its existing case manifest before treating any run as final: `python3 scripts/case_workspace.py register-research --workspace <business-root> --case <id> --input <assignment.json> --decision-id <id> --reason <reason>`. A v1 assignment uses one matching parent study. If historical reviewed studies have narrower decisions or segments, use a v2 composed assignment: keep each old study unchanged, add an honestly scoped target study with `execution_contract_version: 4`, give each declared capture one primary target-study query-review owner, and bind required question/locale/frame cells. A historical source may be digest-bound in both studies but counts once at case level; adjacent/context studies cannot close target cells. Run `validate_research_completion.py --check assignment` after revisions. A small source pack never closes a broader request.
2. Before calling providers, write or reuse the executable query plan and customer-feedback source matrix. Show the user the proposed jobs, roles, locales, source families, contrary/positive searches and the first bounded allocation. Query counts are initial work allocations, not quality or spend thresholds. Check applicable verified entities and source access gates.
3. Verify relevant endpoints, using a successful actual content capture when available. A credential, balance or search-only check does not prove comment access. For project Firecrawl CLI calls use `python3 scripts/firecrawl_project.py ...` so `FIRECRAWL_API_KEY_HGINVESTOR` is selected. Public Facebook capture still requires the current signed review bundle. Preserve unavailable sources as gaps and try an applicable supported fallback.
4. Execute the planned queries and selected conversation capture. Inspect the provider query ledger, raw source pages, comments and replies. For Reddit, check that selected discussions span the planned query intents and are not copies of one opening post; increase `--reddit-comment-posts` or use a linked refinement when a material intent lacks customer conversations. Resume interrupted work with the same plan/settings; a changed plan starts a linked follow-up. Record actual query/cell outcomes and unexpanded discussion portions.
5. Check collection before treating it as done:

   ```bash
   python3 scripts/evidence_scout/validate_research_completion.py --workspace <case-or-legacy-root> --run-dir <collector-run> --check collection --json
   ```

   Exit 0 proves the declared capture ran for its scope; it does not validate a customer claim. Exit 1 means partial work, exit 2 invalid inputs. Follow `next_actions`, not a stale manifest sentence or provider count. Search failures and valid empty results are different outcomes.
6. Review source-linked experiences, including a purposeful sample of rejected/adjacent material. Preserve original language, speaker, chronology, success and contrary cases. Build the existing experience ledger, source review, source coverage, U/R synthesis and claim review. Separate creator/supplier voice and engagement from firsthand customer experience. Reconcile query/cell outcomes with reviewed evidence; refine searches when material questions remain. If not every retrieved item is reviewed, use the versioned sampling contract in the result row: exact population, selected and excluded IDs, reasons, strata, selected-item reviews, rejection audit and limitations. Counts alone do not establish a valid sample. Claims may use only reviewed accepted items; sampled-out material cannot support prevalence.
   For a registered case, each low-yield or adjacent-only topic cell needs a `search_resolution` in its existing result row: `status` (`refine`, `primary_research_needed`, or observed `access_limited`), specific `reason`, executed `query_ids`, and the distinguishing `next_observation`. `refine` remains open until its follow-up is captured and reviewed. After one bounded, targeted refinement, inspect whether it found a source-local target episode or exposed a concrete new public source route. If neither happened, change the reviewed resolution to `primary_research_needed` instead of repeating broad search. Record why the public route is exhausted; a provider failure alone is access-limited, not exhaustion. Prepare a case-specific unpaid `market_research/interviews/recruitment-plan.md` using `templates/project/primary-research-handoff.md`. Each unresolved cell needs a named target participant, recent firsthand screen, unpaid access route, non-leading episode questions, the exact distinguishing observation from the reviewed result, and a decision rule. Do not treat the route as completed interviews or outreach authorization. For `primary_research_needed`, bind the existing source plan's `primary_research_handoff` to `{path, sha256, cell_ids}` using the case-local workspace-relative path, current SHA-256 digest and all cells with that resolution. The research check remains partial if this handoff is missing, vague, inconsistent or changed.
   A v4 target study additionally needs exactly one `query_reviews` row for **each** attempted topic query, including zero-hit and failed queries, even when another query in the cell found useful evidence. Each row gives `query_id`, `status` (`reviewed`, `refine`, `primary_research_needed`, `access_limited`), exact captured `record_ids`, source-reviewed `reviewed_ids`, per-provider `provider_outcomes`, a named `reviewer`, an observed `reason`, and a distinguishing `next_observation`. A `refine` row is unfinished; primary-research handoffs remain bound through the same case-local plan field. Do not mark a query `reviewed` because a search snippet or different query looked useful. When a provider returned results that retention discarded, inspect the raw capture and add `raw_result_reviews` under that query review: provider, current raw digest, returned/retained counts, reviewer and reason. For Reddit, identify every returned candidate by its stable ID and original URL with an `excluded`, `retained` or `promote` disposition and reason. A promoted candidate must enter retained evidence and source review before closure. A true zero-result query needs no raw-result review. A v4 `applicable: false` entity lane also needs `applicability_review` with reviewer/date, exact entity/locale/lane, observed query, retained case-local source URL/path/SHA-256/span, observed fact and specific reason. Provider failure means access-limited applicable coverage, not inapplicability.
   Generate a review-prioritization view when query memberships exist: `python3 scripts/evidence_scout/build_research_yield.py --plan <query-plan.json> --evidence <evidence.jsonl> --source-review <source-review.json> --out <research-yield.json>`. It is a derived view, not a source of independent-episode counts or a completion receipt.
7. Link any refined or entity-specific capture runs in the existing customer-feedback source plan with `capture_inputs`: each row has the workspace-relative `run_dir` and an `artifact_digests` object mapping `query_plan.json`, `summary.json`, `evidence.jsonl` and `irrelevant.jsonl` to their SHA-256 digests. Only bind runs that pass the collection check and whose case, entity, locale and reviewed source locator match the pack. Reconcile exact captured IDs before accepting the pack. Then run the research check on its parent run. For market discovery, its VOC pack lives under the discovery run and collection under `<run>/evidence/`:

   ```bash
   python3 scripts/evidence_scout/validate_research_completion.py --workspace <case-or-legacy-root> --run-dir <research-run> --check research --json
   ```

   A reviewed `insufficient_evidence` outcome is valid research if execution was complete. It cannot pass `problem_validation`. A partial finding can be shared with named unfinished sources and limits, without a full-completion claim. For episode-sampled cells, `unextracted_document_ids` must equal captured document IDs minus the parent documents of extracted episodes; a partly reviewed multi-speaker page may still need more speaker review even after its first episode is extracted. In a composed v2 case, inspect `shared_source_overlaps` from the assignment check. The same original URL in adjacent and target ledgers counts once; add an explicit `overlap_reviews` disposition for each detected overlap before delivery, preserving a distinct interpretation as a conflict rather than independent corroboration.
   For a registered case, run `python3 scripts/evidence_scout/build_case_closeout.py --workspace <business-root> --case <id> --json` after each review batch. It derives exact query IDs, captured record IDs, original URLs and entity-lane work from current authorities; it does not write a review or approve evidence. Work through its pending items, rerun the authoritative checks, and publish reviewed insights progressively. A `next_stage_limitation` item can remain after desk closure and names the external observation still needed.
8. For a registered Business case, update the one `case_insights.md` progressively. Publish after each coherent batch of reviewed findings, deep-dive answers or material corrections; do not append a technical activity log. Keep supported findings readable, qualify provisional conclusions, include answered questions and conflicts, and state remaining questions in plain language. A progress publication must bind and disposition the current inventory, with pending inputs explicitly marked. Run the insights validator and publish transaction for each revision. A current progress snapshot is useful to readers but is not final delivery; completion remains separate. Newly captured evidence must not enter claims before review, and a change to already bound support makes the affected publication stale until revised.
   Use the v2 citation contract in [case-insights.md](case-insights.md) for reviewed VOC claims. Bind the exact completed run's claim ledger, source review and evidence into the publication; link material claims to their inspected original sources beside the claim. Prepare the exact rendered output and obtain a separate reviewer record before completed case delivery. A current document for another run cannot close this run. Short answers enter insights directly; substantial answers belong under `market_research/deep_dives/` and their business implications must enter insights. A selected plan whose case insights become stale is pending review.
9. In the final handoff state executed scope, what the reviewed episodes support, contrary cases, access/coverage gaps, claim readiness, and the current insights path. If any check is partial or invalid, name the missing work and do not call the assignment fully rerun. Keep case-specific business-plan commitments behind the current problem-validation receipt.
   Keep each case in the queue until it has one explicit reviewed outcome: **provisional plan published** (eligible reviewed case evidence, sourced segment/journey/pain analyses, nine-section case appraisal and refreshed insights), **more targeted research required** (named open query/source cell and distinguishing observation), or **evidence insufficient** (executed and reviewed desk scope, exact customer or commercial observation missing, and a bounded primary-research handoff). An outcome is a progress label; it does not mean the case is closed. The queue's `closure_status` is `interim` while delivery is partial or blocking source work remains. Do not label a case evidence-insufficient just because collection is complete or a review pack has not been written. Re-run the queue and authoritative gates after any new capture or publication. Use `build_case_closeout.py --workspace <business-root> --case <id> --require-terminal` as the strict stop check; exit 1 means delivery or blocking research remains open. Report the outcome and first blocking item without claiming closure.
   Before final delivery, use `--check assignment` and `--check delivery` on the registered parent run. Prepare the exact final publication bundle and have a separate reviewer inspect original passages, roles, countries, numbers, counterevidence and omissions. A completed desk-research scope with `primary_research_needed` is an insufficient-evidence outcome, not a passed problem gate.

The completion checker is read-only. Stage and insights publication remain the authoritative writes. Its deterministic checks verify provenance and coverage declarations; an analyst still has to judge the meaning of passages. Never infer market prevalence, demand or willingness to pay from comment counts, duplicate posts or a successful API call.
